DNSite

A proof of concept: this entire page was fetched from DNS TXT records, decompressed, and stitched back together in your browser-facing client.

How it works

DNS is usually used for names and addresses. TXT records can also carry arbitrary text — so with a small client, you can treat the DNS tree as a read-only object store for a webpage.

  1. Compress The HTML is gzip-compressed, then base64-encoded so it survives as TXT text.
  2. Fragment The payload is split into small chunks (about 200 bytes) that fit typical provider limits for a single TXT string.
  3. Link Each record points at the next name, like a linked list: site → p1.site → p2.site → … → end.
  4. Resolve A client walks the chain with ordinary TXT lookups, joins the bodies, base64-decodes, gunzips, and renders the HTML.

On the wire

Every fragment shares one header shape. The encoding tag tells the client how to rebuild the page; next= is the pointer, or end stops the walk. 

dnsite2|gzb64|next=p1.site.example.com|<chunk>
dnsite2|gzb64|next=p2.site.example.com|<chunk>
dnsite2|gzb64|end|<chunk>

Publish those as TXT records (for example via a BIND zone snippet), then run dnsite get site.example.com --open.

Why this is a proof of concept

It is intentionally constrained. The point is to show that a resolvable name can carry a whole document — not to replace a CDN.

  • TXT size and label counts are small; large sites need many records.
  • Updates mean rewriting the chain; there is no partial patch story.
  • Latency is one lookup per fragment unless you parallelize cleverly.
  • Anyone who can query DNS can read the page — treat it as public.
  • Still useful for demos, easter eggs, tiny status pages, or art projects.
